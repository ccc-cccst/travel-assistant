# 团队协作规则

版本：v1，2026-10-22。这是一份三人课程项目的协作提案，经团队查看、合并后采用。

目标：每项任务有人负责，修改能安全合并，实验有证据，主分支能按说明运行。

## 1. 任务与分工

开始编码前，在 Issue 或已有任务板写清四件事：问题、负责人、影响的模块、验收例子。小型文档修正可直接写在 PR，不必重复建 Issue。

任务尽量拆成一到两次工作即可交付的范围。例如“实现午餐额外通勤诊断”，而不是“完成整个评价系统”。状态统一为：待开始 → 进行中 → 待评审 → 已完成；阻塞时注明原因和需要的配合。

| 方向 | 主要范围 | 交接内容 |
| --- | --- | --- |
| 数据与工具 | 地点、路线、天气、评论标签、缓存与来源 | 字段含义、单位、适用时间、缺失和错误状态 |
| 规划与验证 | 候选、硬约束、体验评价、局部修复 | 行程结构、诊断结果、修改范围和检查结果 |
| 交互与实验 | 标签、需求确认、时间线、修改差异、实验汇总 | 用户输入、锁定安排、验收案例和对照结果 |

具体负责人和评审人在任务中指定，不把模块变成只有一个人能修改的区域。跨模块改字段、单位或返回格式时，先说明新旧示例及受影响调用方，在同一 PR 提供兼容处理或同步修改。

## 2. 分支与提交

- `main` 保存团队已确认版本；日常功能、实验和文档修改从最新 `main` 建任务分支。
- 分支使用 `feat/`、`fix/`、`docs/`、`exp/`、`chore/` 前缀，例如 `fix/visit-duration`。
- 每人使用自己的克隆目录。多人或多个 AI 会话同时工作时使用独立目录或工作树，不共享会被反复切换的工作区。
- 一个分支聚焦一项任务，不顺手改其他模块或全库格式化。
- 提交说明写清修改，例如 `fix: 使用推荐时长替代固定90分钟`。
- 只暂存本次任务文件；提交前查看工作区和暂存差异，不覆盖同伴未提交的修改。
- 不向 `main` 强制推送，不随意重写共享历史。冲突需要确认双方意图，不能简单整份覆盖。

命令和 GitHub Desktop 步骤见 [协作指南](../CONTRIBUTING.md)。

## 3. PR 与评审

PR 说明四件事：问题、修改后的行为、实际验证结果、限制。未验证项明确写出。

至少一位非作者成员检查后合并；评审重点是需求、接口、验证和风险。重要修改后请评审人重新查看。AI 生成的代码和 AI 评审建议由使用它的成员核对，不能代替成员评审。

默认使用 Squash and merge，让一项任务在 `main` 形成一条清晰记录。合并后更新任务状态；其他成员同步 `main` 后开始下一项任务。紧急修复仍走小型 PR，尽快找同伴检查。

以上是团队约定，不会自动开启 GitHub 强制限制。仓库所有者可为 `main` 设置：要求 PR、至少一位批准、处理完讨论、禁止强制推送。本提案未更改仓库权限或配置自动检查。

## 4. 代码与验证

- 保留上游作者、许可和 `UPSTREAM.json`。修改 `ChinaTravel/` 时说明与原始版本的差异。
- 修改逻辑时使用能重现问题的案例，记录修改前后结果；需要回归保护时增加有意义的测试。
- 纯文档修改检查内容、链接和命令，不强制跑完整数据集或写同义测试。
- 修改解析、单位、时间、预算或锁定安排时，验证相关边界和失败情况。
- 局部修复后重新检查完整行程，防止破坏交通、预算或其他预约。
- 改依赖时同步安装说明及对应清单，检查新成员能否按说明使用；不顺手升级全部依赖。
- “代码能执行”“官方检查通过”“用户体验好”分别报告。

## 5. 数据、密钥与接口开销

- 密钥只在本机隐藏输入或通过进程环境变量使用，不写进代码、截图、Issue、PR 或日志。各自使用自己的账号与密钥。
- 数据、虚拟环境、原始响应和完整日志留在本机；只提交允许共享的样本 ID、脱敏摘要、小型人工整理结果和代码。
- 新数据说明来源、获取时间、适用日期、单位和使用限制。评论观点不能直接证明今天营业或交通可达。
- 缺失值、冲突和待核验信息明确表示，不能默认成免费、零分钟或全天开放。模型推断与检索事实分别记录。
- 真实 API 实验应在当前任务或既有授权的样本、并发、时限和费用范围内；先离线或少量试跑，没有明确预算时不自动扩大到全量。
- 暂存文件后运行 `python scripts/check_publish.py`，并人工查看差异；自动检查不覆盖所有秘密格式。

## 6. 实验与体验评价

使用 [实验记录模板](EXPERIMENT_TEMPLATE.md)，记录代码提交、模型 ID 与版本声明、数据版本与样本 ID、方法开关、预算、指标和失败情况。

- 原始基线、仅修复实现问题的版本、加入新方法的版本分开比较。尽量固定模型、数据和资源上限，差异必须说明。
- 调试样本用于开发，正式验证另固定样本。参考约束用于评价；Oracle 诊断单独标注，不能混入普通规划结果。
- 超时、缺失和错误保留在总样本中；额外报告双方均成功样本上的质量，写清分母，不只展示成功例子。
- 体验分项报告交通负担、绕行、停留适配、每日节奏和偏好覆盖。用户确认的休息日、自由时间和专程美食不自动扣分。
- 新阈值与权重说明依据及适用场景，模型评分仅作辅助，需要规则核验或人工评价支撑。
- 动态数据保存快照或版本；局部修复报告成功率、修改量、锁定安排保留及修复后完整检查。
- 小样本写为探索发现，不代表全数据集或原论文历史版本。未运行的实验不写成已通过。

## 7. 完成标准

满足以下条件才将任务标为“已完成”：

1. 验收例子已执行，结果及限制写入 PR。
2. 与本次修改相关的检查通过；未执行或受阻的检查已说明。
3. 必要的接口、说明和实验记录已同步。
4. 暂存内容经过敏感信息检查，没有混入本机文件。
5. 至少一位同伴检查，并已合并到 `main`。

本地代码、待评审 PR 和模拟演示分别标明状态，避免成员误以为已交付。

## 8. 沟通与规则调整

有实质进展、范围变化或阻塞时更新三行：已完成、下一步、需要谁配合。会议结束记录决定、负责人和下一步。

规则通过小型 PR 调整。示例、默认选择和建议可在任务中说明理由后调整；用户明确要求与现有授权优先，AI 不应因推测性风险反复要求确认。

GitHub 评审限制官方说明：https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews
