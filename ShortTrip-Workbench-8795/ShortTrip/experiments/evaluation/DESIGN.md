# ShortTrip 独立实验评测方案 v0

日期：2026-11-11。状态：v0参考协议；基础实现和离线回放已完成，使用方式及实际范围见README.md。本文的权重、阈值和扩展样本规模仍是待校准设置，不是已验证的用户满意度标准。

目标：让不同搜索策略、参数和模型的实验使用同一套评价标准，快速判断可行性、体验、偏好和计算成本如何变化。评测器读取完整实验产物，在规划结束后运行；暂不把新评分接入DFS选点、候选选择或RL训练。

借鉴 TripScore 的可行性门控、质量与偏好分开、规则与语义结合、人工比较校准的结构。下文的指标适配、权重和统计协议是 ShortTrip 的设计，不是论文原样复现。
论文：https://arxiv.org/html/2510.09011v4 ，重点第3.2节、附录N/O/P。

## 1. 输入、流程和运行范围

```mermaid
flowchart LR
    A[冻结需求与资源] --> C[离线独立校验]
    B[规划输出与时间事件] --> C
    C --> D[规则质量与偏好评分]
    C --> E[缓存的语义评价]
    D --> F[同需求配对比较]
    E --> F
    F --> G[总表、明细和预算曲线]
```

每个实验预先冻结：需求集合、资源快照、需求解释、评分版本、模型与提示词、预算、初始顺序、重复次数、候选选择方式。原始自然语言始终保留。相同实验中的方法使用相同资料，不能事后按结果修改评分。

两类运行范围分别报告：

- `frozen_search`：从同一个已准备状态开始，包含该次方法特有初始化、排序、调度、路线查询、在线校验/评分和结果发布。用于EXP003等搜索机制对照。
- `end_to_end`：从接受需求开始，包含翻译、检索、模型请求、交通酒店选择、搜索和结果发布。由一次连续运行测量，不能拼接旧缓存历史耗时。

冷启动/服务热启动、缓存模式、机器、线程数等进入manifest。同一对照不混用实调模型、精确缓存回放和纯规则模式。

## 2. 四类主指标及分母

### 2.1 预算内合法产出率

对需求q、重复r、方法m、预算B，取截止B之前最后一次已发布的选中方案。必须同时满足：

1. 是完整方案，且有可核验的发布时刻；
2. 在预算内已完成规划器自身的选择并发布；
3. 离线独立校验通过。

离线校验可在B之后完成，但不得用B之后生成的方案或重新选择的候选补位。

`feasible_by_budget = 合格的预算内已发布方案数 / 全部已完成的预定运行数`。

正式报告先在每个需求内部对重复/初始顺序求平均，再对需求等权平均，避免某需求运行次数多就占更大权重。未执行的预定运行标为pending并显示报告不完整，不能填成功或失败；已执行后崩溃、无结果的运行保留在分母。

必须保留四种情况：无方案、方案不合法、校验未知/报错、合法。只有最后一种计为确认成功。未知单列，不宣称算法一定违反约束。

独立校验组合：schema与实体信息、原常识检查、C审计、数据集标准硬约束、事先复核的需求清单。标准约束只进入评测器，不能泄露给planner；不能仅信任planner自己生成的DSL。若数据集标签与自然语言有歧义，在看新方法结果前记录解释并冻结。

没有某类约束属于N/A，不是失败；需要的数据缺失属于unknown，不得自动通过。C审计的单目的地往返假设只能用于兼容案例，多目的地/无城际交通案例需新的校验配置。

### 2.2 行程质量与偏好

只对已确认合法的方案报告正式质量与偏好分；非法/无结果记null而不是0。所有分项保留原始数值、适用状态、覆盖率、证据和评分版本。

同时输出：各方法成功案例均分，以及双方共同成功需求上的配对分差。前者是描述统计，不能据此宣称新方法更好：只解决简单需求的方法可能均分更高。

### 2.3 同需求胜／平／负

匹配键为需求、资源快照、运行范围、预算、初始顺序、重复/seed、评价版本。同一需求的近义改写与同一源需求的变体归为同一统计组。

| 比较情况 | 判定 |
| --- | --- |
| 一方确认合法，另一方确认失败/无结果 | 合法方胜 |
| 双方确认合法且同一评分配置完整 | 比较综合分S；差值大于3分为胜，小于-3分为负，其余为实际近似平局 |
| 双方均确认失败/无结果 | `both_failed`单列，不记质量平局 |
| 一方校验未知、缺少必要评分或时间证据 | `unresolved`单列，不自动判负 |

3分是0—100尺度下的v0工程容差，尚未人工校准；不是显著性阈值。在开发集上确定后，正式测试期间不能修改。

令N=W+T+L+both_failed+unresolved。主指标明确为`确认获胜占比=W/N`，平局不折半计入，未决也不算输；五类比例一起显示。另报已决比较中的`W/(W+T+L)`，以及双方合法且可比较子集的胜率和分母。分母为0则N/A。每项先在需求内计算，再对需求等权，不把一个需求的多个顺序当成不同用户案例。

### 2.4 耗时和超时

分别记录：首次发布且事后确认合法的方案时间、最终交付时间、完整进程结束时间、规划模型调用量/耗时、离线评测耗时/模型调用量。

- `budget_exhausted`：用完预定搜索预算，是anytime算法的正常停止原因之一。
- `first_result_late`：约定时限内没有对外可读的完整方案快照；是否独立合法另由合法产出率判定。
- `final_delivery_late`：最终选中方案及“规划已结束”确认超过时限才发布，或始终没有最终发布；此前有快照时，仍可能按时提供过合法方案。仅内部日志清理/进程退出较晚不算最终交付晚。
- `hard_timeout`：由外部控制器强制停止；是否存在截止前已发布合法快照单独记录。
- `error`：异常结束；不得伪装成“搜索空间无解”。

因此“触预算率”“首结果晚到率”“最终交付晚到率”“硬超时率”分别报告。存在合法结果与触预算/最终交付晚到不是互斥状态；但是晚到的新结果不能倒算成预算内成功。

所有已执行运行都进入耗时和停止原因统计。首次合法结果时间对未找到者记为截尾，不把失败者删掉后仅用成功均值比较快慢。小样本报告中位数与范围；足够样本再加P90，均附样本数。

离线评分成本单列；如果未来把评分放进planner选优，这些在线调用必须计入规划时间。

## 3. 两个明确的评分配置

### 3.1 `fast_rules_v0`：快速回归

CPU计算规则质量Q_rule，以及有明确结构化依据的P_rule；保留旧`total_penalty`作为历史对照。默认不调用任何模型，也不自动启动Qwen。

缺少语义评价时不伪造完整分：质量字段明确标为Q_rule；若某项明确偏好只能靠语义评价，P_rule标partial，不能声称已经测量完整偏好满足。

### 3.2 `full_v0`：阶段性实验结论

在同一规则特征上增加体验评价和无法规则化的明确软需求，得到Q_full与P_full。两个配置使用不同profile_id，不把Q_rule和Q_full直接比较或混排。

语义模型做成可替换配置。沿用本地Qwen的方向，但需要先通过人工一致性与输出稳定性检查；本次不恢复GPU。TripScore所用Gemini可以作为今后授权的另一评测配置，不默认发生外部API调用。模型不可用时full结果pending，fast报告仍可生成。

## 4. 质量分Q的可实现初稿

以下尺度均0—100；权重是待校准的工程默认值，不宣称代表真实满意度。

| 子项 | v0计算定义 | full权重 |
| --- | --- | ---: |
| 交通负担T | `100 * clip(1 - M/A, 0, 1)`；M为全程市内实际交通分钟，A为可安排时间总分钟 | 0.30 |
| 节奏R | 每天忙碌比例r与目标区间比较，按下方分段函数计分，再按可安排分钟加权 | 0.25 |
| 住宿稳定H | `100 * (1 - 不必要同城换店次数 / 住宿夜数)`，截断至0—100 | 0.10 |
| 不重复U | `100 * (1 - 非必要重复景点访问次数 / 景点访问次数)` | 0.10 |
| 体验价值E | 对目的地体验、游览充分性及主题连贯性做0—4分语义评价，乘25 | 0.25 |

可安排区间集合I_d由需求中的日期/活动时间窗、已锁定事项、抵达返程与必要接驳收缩得到，A_d为其区间长度之和，A=sum(A_d)；不因为待评价方案少排景点就缩短A。默认活动窗口08:00—21:00，用户夜游、晚起或休息要求覆盖默认设置，覆盖关系预先写入案例配置。活动/交通的实际总分钟仍另行完整报告，不能把窗口外路程直接丢弃。

节奏：先对景点、餐饮、市内交通区间求并集，再与I_d取交集，以该交集长度作为忙碌分钟；同时报告窗口外活动/交通分钟，不使其从交通原始成本消失。令r为忙碌分钟/A_d，保证r∈[0,1]。默认目标区间[l,u]=[0.4,0.8]：

`f(r)=clip(r/l,0,1)`（r<l）；区间内为1；`f(r)=clip((1-r)/(1-u),0,1)`（r>u）；R为100乘以按A_d加权的平均f。配置要求0≤l≤u≤1，按分支求值；l=0时不进入左分支，u=1时不进入右分支，不预先计算两个除法。

显式节奏/休息要求优先：使用该案例预先定义的区间，不让通用“充实”默认与用户的轻松偏好互相惩罚。A_d为0的锁定日不参与节奏平均；全程无旅游活动需求时使用单独适用性配置，不强迫生成景点。

H中的必要换店（换城、用户明确要求）与U中的必要重访（用户明确要求、同一参观被拆成连续片段）不罚。无住宿/景点的合法任务可标N/A，但适用集合由需求决定，不能因为某方案遗漏住宿/景点就移除低分项。

零分母口径：A=0且该任务确无可安排游览时，T/R按预先确定的任务配置为N/A；仍需游览却A=0时标配置/时间数据未知，不算满分。必要住宿为0夜的遗漏由硬校验处理，无需住宿的任务H为N/A。U适用但景点访问数为0时U=0并记empty_attractions；非必要重复次数只计第二次及以后的非必要访问。所有适用权重之和为0时Q为N/A，不除零、不补100。

`Q_full = sum(w_i * score_i) / sum(w_i)`，只按事先确定的适用集合计算。
`Q_rule`固定使用T/R/H/U并归一化其权重；不能把本来需要的未知项临时删掉再归一化。E本就不适用时按冻结适用集合处理；E适用但缺评分时Q_full为null。任一配置所需规则指标未知时该配置Q为null，仍输出已知明细与覆盖率。

E的固定量表初稿：0=没有可识别且符合请求的游览体验；1=安排明显敷衍或缺少足够体验；2=基本合理；3=体验充分且主题/搭配合理；4=在天数和需求约束下体验充分、选择有明确价值。要求证据引用活动ID或资源字段，缺证据输出unknown；休息、单主题深度游不能因少景点或低多样性自动扣分。评测输入删除方法名和无关宣传文字，避免奖励文案长度。

完整报告另外列出交通分钟/距离、步行、游玩分钟、空档、每日活动量、换店、重复、未知项。Q不是这些原始指标的替代物，也不将“交通最短”定义为绝对最好。

## 5. 偏好分P与综合比较分S

每个需求预先生成并人工复核`requirements`：原文证据、hard/soft、目标、适用范围、权重、验证方式。未表达的喜好不补成用户事实；只有硬约束、没有软偏好时P为N/A。

| 明确软偏好 | 拟定判定 |
| --- | --- |
| 景点兴趣 | 匹配任一指定标签的独立景点数/独立景点总数；标签表先冻结，未知标签不按不匹配处理 |
| 旅行节奏 | 使用该案例的目标区间和第4节的连续偏离函数，按天评估 |
| 体力 | 优先用步行时间/距离及已知活动强度，对预先定义的个人目标区间评分；不能把标签缺失当轻松 |
| 住宿舒适/价格偏好 | 对实际星级、设施、位置或价格目标做字段比较；总预算上限仍由硬校验负责，不能以星级替代真实总费用 |
| 美食、主题、其他自由文本 | 拆成有原文依据的偏好条目；可规则判断的直接计算，其余用冻结语义量表 |

每条软偏好得到p_j∈[0,1]。语义条目用0/0.25/0.5/0.75/1表示未满足至充分满足，并返回证据；默认每条等权，原文明确“尤其/优先”的条目可在预处理时赋2，正式运行后不更改。

每个冻结requirement必须明确`feature、mapping、thresholds、aggregation、missing_policy`。节奏按A_d加权，体力按日等权且明确哪些天适用；住宿按夜加权，多设施要求按字段等权。分类/设施用0或1匹配；单边软上限采用`p=1`（x≤目标），超出时`p=clip(1-(x-目标)/容忍尺度,0,1)`，尺度必须为正且预先登记；双边偏好用明确端点的分段函数。没有足够信息确定目标、尺度或映射时标unconfigured，完整P/S为null，不允许实现者现场猜参数。

`P = 100 * sum(a_j*p_j)/sum(a_j)`。有需要但资料未知的条目不能丢弃或补0/1，完整P为null，报告部分分项和已知权重覆盖率。

用于同需求排序的探索性综合分：存在且完整评估软偏好时`S=0.5Q+0.5P`；没有软偏好时`S=Q`。明确有软偏好但暂未评完时S为null，不能套用“无偏好”的公式。只比较同一profile内的S；质量和偏好仍分别报告，避免综合分掩盖退步。

这套S的权重、3分平局容差须经后续盲选校准；在校准前，报告标注“工程代理评分”，不能直接称为用户满意度或训练奖励。

## 6. 语义评分如何保持可复用、快速

每个不同的`需求 + 规范化行程 + 资源快照 + 评分版本 + 模型版本 + 提示词版本 + 推理参数`构成缓存键。相同行程跨方法/重复出现只评一次，保留原始响应、耗时、token、解析状态和原始指纹。

v0建议一个结构化请求返回E与全部语义偏好条目的分数/证据/unknown；固定temperature=0，不要求思维链。仅评价完整候选，默认评各预算时点实际选中的不同方案，避免给全部161条候选重复调用模型。

格式失败最多重试1次，记录两次耗时；仍失败记unknown，不自动换模型或让缺失项满分。缓存去重只去除非语义字段，保留日期、顺序、交通和活动时长；不同输入不误并。

校准时抽取20%的样本重新调用3次，统计分数波动与胜负翻转。人工盲选隐藏方法身份，并交换左右顺序检查偏差。可保留“差不多/无法判断”，不强迫所有样本分胜负。

## 7. 预算曲线、所选结果与候选池诊断

主结果评价算法当时已发布的选中方案，而不是事后用新评分在整个候选池中挑最优。离线重新选优单列为`pool_oracle`诊断，用于区分“搜不到好方案”和“搜到了但原选择器没有选中”。

拟定搜索墙钟预算为5秒和15秒，各自作为独立运行；可额外记录1、3、5、10、15秒的只读快照，超过实际停止时间沿用最后已发布结果并注明已停止。在实际截止后生成的新候选永远不能回填。

同时保留200个DFS入口、180秒保护的工作量对照，用来衔接EXP001；它不属于同墙钟成本比较。候选池容量与搜索停止条件分开，两种搜索方法使用相同配置。

预算曲线至少包含：合法产出率、已发布方案的Q/P/S、首次合法结果时间、节点与路线调用数。新评分下的所选方案分数可以下降，不能画成事后最优包络；只把明确标注的候选池上界诊断画成单调曲线。

## 8. 数据接口与旧实验兼容

建议目录：`artifacts/evaluation/<eval_id>/`，输出拒绝覆盖已有评测。

| 产物 | 内容 |
| --- | --- |
| `manifest.json` | 需求/资源/实现/评分/模型哈希，运行范围、计划案例、预算与重复协议 |
| `plan_scores.jsonl` | run与plan指纹、逐项合法性、原始指标、Q/P/S、适用性、unknown、证据 |
| `run_metrics.jsonl` | 开始/截止/发布时刻、停止原因、预算内合法性、首次合法时间、模型与评测成本 |
| `pairs.jsonl` | 匹配键、胜平负或未决原因、配对分差 |
| `REPORT.md` | 总表、共同成功子集、失败分类、覆盖率、预算曲线与案例链接 |
| `judge_cache/` | 完整版本化请求与响应缓存；只在语义配置运行时产生 |

新增事件至少包括：`run_started`、`search_started`、`candidate_validated`、`candidate_scored`、`incumbent_published`、`deadline_reached`、`run_finished`。候选相关事件带fingerprint；统一使用相对同一monotonic起点的`at_seconds`，持续时间另叫`duration_seconds`。发布需有可被外部控制器读取的快照，防止进程退出后才补选。

对现有产物的核查结论：

- `prefix_probe`已有summary、candidate指纹、selected、发现曲线和事件，足以做结果回放与部分曲线重建。`first_candidate`是内部校验/软评分后入池时间，不是端到端首个独立合法结果时间。
- `candidate_added`事件尚无fingerprint；可以在计数和顺序完全核验后与候选ordinal关联，但这只能证明入池，不能证明已对外交付。`selected.json`无发布时刻，旧结果标`legacy_posthoc`，严格预算内交付指标为unknown。
- `branch_exit.elapsed_seconds`是分支持续时间，覆盖了通常的累计时间语义；导入器必须按事件类型解释，不能拿整列当统一时间轴。
- `timing_probe`的冻结后搜索时间、driver时间、历史模型耗时不能拼成真实端到端时延。
- 候选池中的`validation`布尔值不能替代独立复核；旧`score.unknown`也不是全部未知指标，需要检查coverage及各原始字段。

准入按协议版本预先分组：legacy_posthoc只进离线质量/回放表，不进入严格预算合法率或严格预算主胜率的分母，不能显示成0%预算成功。新协议的运行若丢失必要时间事件则保留为测量unknown，不允许事后改标legacy来剔除坏结果。

可复用入口：`experiments/prefix_probe/audit.py`的数据集标准约束审计、`chinatravel/evaluation/commonsense_constraint.py`、`chinatravel/symbol_verification/hard_constraint.py`、`experiments/c_only/rules.py`、`chinatravel/soft_constraints/scoring.py`。复用底层函数，避免调用会启动规划或写固定生产输出的worker入口。

## 9. 首轮验证范围与判读

现有查询清单有10个需求（easy_1—5、human_1—5）；已经有冻结搜索证据的独立需求只有easy_1。EXP002复制的同一冻结状态不算新需求，其多次运行也不能算多需求验证。

分三步落地：

1. **离线接通**：读取EXP001/EXP002已有产物，验证独立校验、原始指标、去重和缺失处理；生成标为legacy的报告，不启动GPU，不声称获得严格端到端预算结果。
2. **冻结评测规则**：以easy_1、easy_4、human_1作为预先指定的开发案例；其余7个案例作初步留出检查，尚未冻结者标待准备。补充跨需求的人工盲选样本，校准权重/平局区间；单个easy_1只用于问题诊断。后续正式泛化评测另选至少20个未用于调参的独立需求，并在运行前固定清单；20只是起步规模，不保证统计功效。
3. **接入EXP003**：补齐预算内发布埋点后，普通DFS与轮转DFS用相同实例、预算、原候选选择器和评分配置比较。现有首三景点的6种顺序用于easy_1敏感性检查，各条件3次交错重复；不把6种顺序当6个独立需求。对其他需求按预先固定的自然顺序开始，确需顺序压力测试时另登记。

报告区间按需求分组重采样；只有一个独立需求时报告重复范围与顺序敏感性，不给具有泛化含义的置信区间。跨配置的探索结果如实保留，最终测试集不用于反复选权重。

判读优先级：先看预算内合法率与未知/超时情况，再看共同成功需求上的Q/P/S及胜平负，最后结合时间和预算曲线。质量提高但合法率下降、或耗时增加时报告具体权衡，不强行宣布单一优胜。减少并列、生成更多候选或首分支覆盖更广都不单独构成成功。
