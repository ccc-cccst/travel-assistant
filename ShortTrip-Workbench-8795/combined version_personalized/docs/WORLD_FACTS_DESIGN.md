# 旅行事实模块的接口与查询设计

2026-11-20。基于已实现的 `WorldFacts` 和 P008 数据审计。本文提出后续接入和性能改造。首版使用本地 V20 数据，规划范围沿用十城配置。西安、厦门的原始数据可用于只读复查。

## 接口

P010 已实现 `WorldFacts.trip_snapshot(spec, limit=12)`，从确认版 TripSpec 生成供构想使用的快照。输出包括需求版本、快照 ID、点名项解析、按方向筛过的静态车次、住宿和用餐候选。路线仍按需调用现有 `route`。批量事实接口和路由对象复用属于后续设计。 [P010 验收与复跑](../result/experiments/P010_trip_world_snapshot/REPORT.md)

一趟规划启动时取得一个带版本的 `WorldSnapshot`。它固定源数据版本、字段归一规则版本和城市规划范围，按需读取用到的记录。任务另记实际采用的证据标识。需求引用保留 `request_id` 和 `request_revision`，同一需求重新确认后可以沿用同一个数据版本，但新的事实需求重新计算。保存行程时同时保存需求版本、快照标识及所引用的证据。后续补查产生新证据，旧方案的引用保留原观测。

沿用 `WorldFacts` 为进程内入口，CLI 和 HTTP 复用同样逻辑。Python 模块直接调用 Python 接口。以下方法是新接入的接口设计。已有 `snapshot`、`place`、`intercity`、`route` 可作为逐项读取的兼容入口复用。

|接口用途|输入|返回|
|---|---|---|
|`open_snapshot(purpose)`|规划或只读复查|带版本的快照标识，规划城市范围和数据覆盖。规划模式沿用当前十城配置。|
|`find_places(snapshot, query)`|城市、类型、精确名称或别名，或检索词与数量|地点 ID、基础卡片和匹配状态。指定地点按名称、别名或 ID 单独解析。普通召回使用计划候选口径。|
|`read_facts(snapshot, queries)`|一批带查询 ID 的地点、城际、接驳或证据查询|按查询 ID 返回事实、状态和来源引用。缺一条时其余结果仍可用。调用者可选择所需字段。|

事实结构只保留消费者需要共享的内容。地点键包含城市、类型和数据内 ID。事实项记录 `fact_id`、值、单位、适用范围和 `evidence_id`。同一批回复复用来源条目，包含快照文件和记录位置或外部观测依据。查询状态区分查到、无记录、歧义、到限和查询失败。证据状态区分快照参考、日期观测、估算和未知。价格的每人、每间、每晚和房型范围需要随值保存。分段营业保留各窗口及来源。

### 批量查询的输入

|`type`|关键字段|取法|
|---|---|---|
|`place_fields`|`place_id`、`fields`、可选的访问日期、票种或入住条件|一次读取营业、价格、停留时长等选定事实。营业时段用当地分钟数表达，跨午夜时允许结束值超过 1440。|
|`intercity`|有向出发地与目的地、模式、日期和可选席别|分别取静态班次、该日期观测与资料不全的记录。每个方向独立。|
|`local_route`|起终点 ID、方式、出发时刻、可选日期和人数|返回预计耗时、费用、路段与来源。为估算或有条件的时间结果保留相应标记。|
|`evidence`|已取得的 `evidence_id`|返回支持显示和复核的详细出处。此查询按引用读取已保存证据。|

例如试排器已经收到构想中的地点 ID，可以一次提交下面两条请求。示例中的地点 ID 来自上海快照，日期仍可未定。

```json
[
  {"id":"attraction-info","type":"place_fields","place_id":"attraction:shanghai:0","fields":["opening","price","recommended_stay"]},
  {"id":"arrival-link","type":"intercity","origin":"南京","destination":"上海","modes":["train"],"travel_date":null}
]
```

回复分别携带这两个 `id` 和各自结果。即使票价未知，营业信息和列车记录也能照常返回。对同批的等价请求先按查询条件合并，再把结果分发到各 `id`。超过调用方剩余时间时，可保留已读结果并明确哪些查询尚未完成。

返回接口保持小。旅行事实查出有哪些地点、营业和费用资料。核心体验、硬软约束、是否满足预算和最终排序由上层决定。当前本地数据可测算静态方案，是否真实营业、当前余票和购买价格仍按证据状态判断。

### 候选定价口径

按现有数据整理口径，已知收费的景点优先保留收费标注。景点缺价时仍可进入推荐候选，收费状态保留待核实。用户点名的景点或影响最终预算和选案的景点，优先按需动态查询。只有来源明确记录免费，或查询确认在适用条件下免费，才按零元核验。动态查询结果同时保存日期、适用票种和来源。查不到依据时保留待核实，避免把未知票价算进已核验预算。

缺有效价格或计价口径的餐厅和酒店从默认候选屏蔽。两类原始记录仍可通过名称或 ID 解析。用户明确点名时可以查看，并说明缺失字段。目录覆盖与默认候选数量分开报告。西安与厦门继续冻结行程规划，两城历史记录仍可只读复查。

默认读取只查本地。动态补查由规划器提交需核实的地点、访问日期及票种等必要条件。比如先从候选中选出两种可比方案，再只查会影响选择的票价。按相同条件去重，并标记数据是否具备动态来源、是否实际发起、是否取得结果。暂时没有可用数据源时，返回原快照证据和待核实字段。

## 各模块怎样使用

|调用方|什么时候读|读什么|
|---|---|---|
|需求理解|用户填写或确认地点时|先解析名字、别名和城市。若一个名字对应多个地点，返回候选供确认。地名匹配可独立完成，无须提前查整趟交通和费用。|
|体验构想|发出整趟构想请求前|按意图和区域取少量卡片，包含地点 ID、名称、区域、类型及会影响选择的时间提示。证据长文本与本地整表留在后台。模型回传 ID，程序即可取详细事实。|
|规划器|地点组合试排或用户点击顺路优化时|先批量读真正参与当前试排的地点、关键交通、营业和费用。普通组合先用近似时长做筛选，紧窗口优先核对必要路段。用户点排序后再批量计算选中地点之间的通行。|
|独立评估|首案与排序结果交付前|从同一快照按事实 ID 取实际方案引用的记录。独立重算费用、时间和接驳，保留证据不足项和对应来源。|
|交互与持久化|展示行程或打开旧方案时|读取保存的方案摘要和证据标识。需要查看详情时再展开来源、参考价或待核实原因。页面刷新复用结果。|

当前 `tripspec_v1` 的具体接缝位于 `TripSpec.items`。业务层把其中已核对的 `destination_city`、`attraction`、`restaurant`、`hotel`、`near_anchor` 和 `appointment` 转成地点查找请求。对明确地点记录 `place_id`，对体验主题或同类景点示例保留检索意图。匹配不确定时保留原文和候选，明确固定的预约地点交用户确认。归一层可以读城市和实体目录，`WorldFacts` 的读取接口只接收结构化查询，不消费整份原文或模型提示词。

例如用户点名上海迪士尼，需求理解只解析实体。构想模块拿它与少量市区候选做跨日搭配。规划器只详细核对已入选组合和关键返程。用户点第二天的顺路优化，才计算第二天选中地点的接驳。网页默认按天展示地点，时间证据留给后台核验。

## 性能改造

当前已有目录、城际查询和市内路线缓存。未命中时，V20 沙盒入口会为城际查询构建 `IntercityTransport`，为市内接驳构建 `Transportation`。在同一进程对上海外滩至豫园的离线出租车样例试查，首次约 1.00 秒，完全相同的请求约 3 毫秒。仅改变出发时刻约 1.06 秒，仅改变人数约 1.15 秒。南京至上海列车查询首次约 0.65 秒，重复约 1 毫秒。上述为单次本地探针，定位的是缓存未命中，不代表规划耗时。

按实际收益实施下列改动。

1. **复用读取与路由对象。** 每个已固定数据版本的工作进程按需加载目录索引、城际表和交通图，后续批次复用。把身份、坐标和分段窗口解析做成按版本缓存的读取结果。保留现有沙盒的坐标、跨水和资料缺失判断。CLI 子进程和网页进程分别加载各自的实例。
2. **按决策阶段读取字段。** 目录搜索和模型卡片只带用得到的字段。规划内部批量读取证据，避免逐地点反复解码同一行。约束紧的日期先取预约与返程等关键接驳。路线候选先按地点和区域缩小范围，再核对具体通行；直线距离仅用于筛选。
3. **把可复用的路线与价格条件分开。** 离线路由先缓存有向端点、交通方式和数据版本对应的拓扑与估算结果。只有数据源明确采用固定速度与票价规则时，才复用时长，并在返回阶段按出发时刻、人数重算展示时刻和车辆数。班次和按日期变化的报价必须按方向、日期、席别或入住口径缓存。对接时变路网后，路线键包含出发时段和对应来源。缓存失败也要保留具体原因与适用版本。
4. **批处理实际需要的路段。** 初次试排查询当前组合和固定安排的关键边。点顺路优化才补查当天已选地点的有向路段。多方案重用相同结果，避免先生成全城距离矩阵。预算耗尽时返回已取得的局部证据和未查询项。

目录索引、路线拓扑和已完成查询按数据与规则版本复用。日期相关报价的缓存键包含方向或地点、目标日期、席别或房间及人数。后续启用动态来源时，根据来源与观测时刻管理缓存有效期。暂时性连接失败或搜索到限保存为查询结果以供诊断，后续可重试。

## 验收

接入前后使用同一批十城原题和 V20 数据。先在现有上海、南京等已验证查询上比较输出，再从原题复跑完整请求。核对 ID、单位、日期、营业窗口和未知状态一致。确认缺价景点仍可被召回且预算保持待核实，缺价餐厅和酒店屏蔽于默认候选并可被地点查询查到。确认跨日期、反方向以及人数变化的费用独立计算。记录首次与重复读取的时间、底层对象初始化次数、实际路线计算数、缓存命中率、发给模型的真实 token、首案等待与顺路排序耗时。同时统计硬约束误放行、误判无解和因证据不足而保留的案例。只有数据语义正确的提速可以纳入结论。

优先交付稳定的读取接口、证据格式与对象复用，然后让体验构想和规划内核接入。更换底层数据库、预计算全城路网或引入实时提供方，由后续覆盖问题和实测耗时决定。
